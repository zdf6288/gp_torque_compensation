# GOAL1 L Current-q Anchored Trajectory

## Purpose

GOAL1 L adds an offline CSV generator for the lab-side case where the robot's current joint position is not exactly the fixed first row of the existing GOAL1 CSV.

The goal is to keep the GOAL1 spatial-rich relative motion shape, but make the generated CSV start at either:

- a manually supplied `--q0`
- one current `/state_parameter` sample from `--from-state`

This avoids asking the operator to manually move the robot to a fixed CSV first `q` before a no-motion state-only preflight.

## Fixed CSV q0 vs Current-q Anchored q0

The fixed GOAL1 CSV starts from the profile's built-in first row. That is useful for repeatable offline generation, but it may not match the real robot's current `q`.

The current-q anchored CSV is generated by:

- first generating the original GOAL1 profile
- computing `delta_q(t) = q_profile(t) - q_profile(0)`
- writing `q_new(t) = q0 + delta_q(t)`

The first CSV row therefore satisfies `q_new(0) == q0`. The original profile-derived `dq`, `ddq`, and optional `jerk` are kept unchanged.

## Safe Generation Workflow

Manual q0 mode:

`python3 scripts/generate_goal1_current_q_anchored_trajectory.py --q0 "0.07,-0.65,0.17,-2.33,-0.11,1.49,0.75" --duration 3.0 --sample-rate 50.0 --profile spatial_rich --prefix goal1_current_q_anchored_3s_50hz --no-plots --fail-on-unsafe`

ROS state mode:

`python3 scripts/generate_goal1_current_q_anchored_trajectory.py --from-state --state-topic /state_parameter --state-timeout-sec 1.0 --duration 3.0 --sample-rate 50.0 --profile spatial_rich --prefix goal1_current_q_anchored_3s_50hz --no-plots --fail-on-unsafe`

State mode only subscribes to `/state_parameter` and reads one state sample. It does not publish any topic, launch any controller, send `/effort_command`, start GP, or move the robot.

Default generation is intentionally short:

- `duration=3.0`
- `sample_rate=50.0`
- `profile=spatial_rich`
- `output_dir=outputs/goal1_joint_trajectory`
- `prefix=goal1_current_q_anchored_3s_50hz`
- plots off by default
- `fail_on_unsafe=true`
- `joint_limit_margin_rad=0.05`

## Output Files

For the default prefix, the generator writes:

- `outputs/goal1_joint_trajectory/goal1_current_q_anchored_3s_50hz.csv`
- `outputs/goal1_joint_trajectory/goal1_current_q_anchored_3s_50hz_summary.json`
- `outputs/goal1_joint_trajectory/goal1_current_q_anchored_3s_50hz_summary.md`

The summaries include q0 source, state topic when applicable, duration, sample rate, profile, row count, q0, first and final q rows, per-joint q min/max, max absolute dq/ddq, safety status, output paths, and the explicit scope statement:

`offline only, no ROS replay, no controller integration, no robot motion`

## Safety Checks

The generator checks:

- `q0` has exactly 7 finite values
- state mode `q` and `dq` each have exactly 7 finite values
- generated `q`, `dq`, `ddq`, and optional `jerk` are finite
- generated `q` stays inside conservative position limits with `--joint-limit-margin-rad`
- max absolute `dq` stays below the existing conservative velocity threshold
- max absolute `ddq` stays below the existing conservative acceleration threshold
- CSV columns match the required `goal1_joint_space_replay.py` fields

These checks are offline screening only. They do not prove controller tracking safety or real Franka safety.

## Lab-side Validation Workflow

After generating the CSV, use a no-motion state-only preflight before considering any later replay review:

`ros2 launch py_controllers goal1_joint_space_replay_launch.py csv_path:=outputs/goal1_joint_trajectory/goal1_current_q_anchored_3s_50hz.csv state_only:=true dry_run:=true start_replay:=false publish_effort:=false`

This command is intended to confirm that the first CSV `q` matches the current `/state_parameter` `q` within tolerance. It does not start `cartesian_impedance`, does not start GP-on, and does not create an `/effort_command` publisher in the state-only path.

Do not use any effort-publishing command until a separate lab-side safety review explicitly approves it.

## Lab Caveat

Known lab-side caveat:

- `cpp_relayer inactive` can create the `/state_parameter` publisher but may not publish a fresh state message.
- `cpp_relayer active` has triggered known `communication_constraints_violation` on the lab machine.
- This communication issue is common enough that GOAL1 validation should not overstate robustness.

The current engineering standard is that one successful run producing usable data is enough to proceed to the next review step. It is not a claim of robust repeated validation or clean shutdown behavior.

## Explicit Scope

GOAL1 L only generates a recordable CSV and summaries. It does not modify `goal1_joint_space_replay.py`, launch safety defaults, `cartesian_impedance.py`, `cpp_relayer.cpp`, torque command logic, or GP behavior.
